## A safety rule keyed to a label that matches nothing cannot fire

Labels are renameable in one command (`fatlabel`). A rule "never write to `BACKUP-ESP`" that matched zero
partitions after a relabel would have read as "no recovery ESPs present" to anything doing a label lookup.
Identify by serial or PARTUUID first, label last.

A **single shared label is itself the defect**: `blkid -t LABEL=<shared> -o device` returns every partition
carrying it, so a consumer must guess which system it means. The bay-numbered form (`RECOV-ESP-<bay>`) is unique
per drive. `scripts/das-wipe-all-drives-and-partition-from-scratch.sh` (v2.1.0+) derives it per drive and refuses
to run if two targets would collide; `tests/test_esp_label_derivation.sh` exercises both the success and the
refusal paths. The vfat UUID being unchanged across a relabel is what proves a relabel, not a reformat.

## Root cause of the incident the rules answer

An ESP sync hook overwrote the recovery drives' independent boot configurations with the host ESP's content.
The hook was generated by this project's `render_esp_hook()` (`indexer/src/setup/templates.rs`) on every
`btrdasd setup --upgrade`, pointing at a script that discovered ESP partitions by label/filesystem and mirrored
the host ESP onto all of them. Disabling `[esp] enabled` in the config left `[esp.hooks]` and the template in
place, so each later `setup --upgrade` silently regenerated the orphan hook; any reintroduction of the script
at the referenced path would have repeated the disaster.

**Fix**: `render_esp_hook()` and its caller, the `EspHooks` struct, the `HookType` enum and the wizard's
hook auto-detect/prompt block were deleted, the live `[esp.hooks]` block removed, the orphan hook deleted.
The project contains no code path that can generate an ESP sync hook, pacman or otherwise.

## What a safe host-ESP mirror looks like (and why it cannot reach a recovery ESP)

A mirror that exists outside this project is safe only if it:

- **enumerates nothing** — source and destination are hardcoded constants; there is no discovery loop, the
  single most important difference from the deleted code, which searched for ESP-shaped partitions and acted on
  whatever it found;
- **cross-checks** that the device mounted at each path is the device the expected label resolves to, and
  refuses on mismatch;
- **hard-blocks any device outside the expected bus class** (the recovery ESPs are USB-attached; a label can be
  renamed, a bus class cannot be renamed into existence);
- copies per file by checksum and deletes from the destination only what the source lacks, so the source
  must be complete before it runs; it offers a dry-run.

Bootloader installation on a host ESP is boot configuration, owned by whoever owns the host's boot setup; this
project owns the recovery ESPs' lifecycle and every operation touching more than one ESP.
